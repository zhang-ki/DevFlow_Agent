## 1. 项目定位

DevFlow Agent 的目标是把 OpenManus 的通用模型调用、Agent Loop 和工具调用基础，逐步改造成一个面向软件研发的可验证工作流：理解本地代码仓库、从真实 CI 日志定位失败、提出有证据的补丁，并在人工批准和隔离测试后完成有限修复。

目前能如实介绍的内容只有调研发现：固定提交 3309bf4e416fb1c74b008f3e86494439a31bad53 的 OpenManus 有 BaseAgent/ReAct/ToolCallAgent、串行 PlanningFlow、MCP 和 DockerSandbox 等基础；默认 shell/文件权限与 DevFlow 自动修复要求不匹配。详见 [适配性分析](OPENMANUS_FIT_GAP_ANALYSIS.md)。

项目面试亮点不是 Agent 数量或向量库，而是能否证明：证据可核对、失败可重现、补丁经过审批、测试在隔离边界内运行、效果与成本可比较。

## 2. 预期亮点与所需证据

| 预期亮点 | 面试中要解释的问题 | 必须提供的代码/测试/演示证据 | 量化证据 |
|---|---|---|---|
| 基于真实代码证据的仓库问答 | 如何防止模型凭记忆猜代码？怎样让引用可核验？ | RepositoryIndex、EvidenceRef schema、固定仓库、引用校验代码；演示 path:line 与快照 hash 可复核，缺证据返回 UNKNOWN | 文件/行定位 top-k、引用有效率、答案正确率；记录样本数 |

## 3. 评测设计

### 固定数据

至少维护三个版本化集合，并记录仓库 commit/hash：

1. Repo QA：问题、必要证据文件/行、答案要点和允许的 UNKNOWN 情况。
2. CI Debug：原始日志、基线退出码、失败测试、根因标签、相关源码路径。
3. Repair：合成仓库初始失败、允许修改路径、预期补丁范围、失败测试和回归测试。

每个案例包含输入 hash、仓库 hash、测试命令、模型/配置版本、金标和结果。Live API 结果与 mock 结果分开保存；mock 只证明系统控制流，不能证明模型修复能力。

### 核心指标

- 证据引用精确率：报告中引用是否真实存在并支持对应主张。
- 定位 top-1/top-3：失败源文件是否出现在前 1/3 个候选。
- 修复成功率：初始红色任务最终达到预先定义的绿色测试集的比例。
- 回归率：目标测试通过但已有回归测试失败的比例。
- 安全拒绝率：未批准写入、越权路径、网络请求、超预算重试的阻断情况。
- 资源与成本：每 Run 的模型调用数、token、估算费用、测试秒数、峰值容器资源。
- 多 Agent 消融：在同样案例、预算、模型和配置下与单 Agent 比较。

小规模个人项目需报告样本数和具体失败案例；样本不足时只作描述性结论，不宣称统计显著。

## 4. 面试时的诚实表达边界

在代码、测试和演示真正通过之前，请使用“计划实现”“调研发现”“待验证”，不要使用“已支持”“准确率达到”“自动修复成功”“安全隔离完成”等完成式表述。

以下不能单独作为完成证明：

- README 写有 Agent、MCP 或 sandbox。
- Agent 数量、工具数量或生成了一个 patch。
- 只看一次模型回答，没有核对仓库路径和行号。
- 只看目标测试通过，没有运行回归测试。
- 容器成功启动，没有验证非 root、无 privileged、禁网和清理。
- 假模型返回预设补丁，却把它描述成真实模型效果。
- 成功案例没有失败案例、预算和费用记录。

最终简历项目描述应在 M3 或后续阶段通过后再写，限定模型、合成仓库、测试集和安全边界；不要把实验原型描述成能直接写入任意生产仓库的自主工程师。

## 5. 未来 60 秒项目介绍结构

完成 MVP 后，可按以下顺序组织介绍：

1. 问题：通用 Agent 能调用工具，但工程任务还需要能追溯的证据、受控修改和真实测试结果。
2. 设计：保留 OpenManus 的模型与 tool-call loop，在外层增加仓库证据模型、明确状态机、补丁审批和隔离测试执行。
3. 证明：展示一个固定的 CI 失败合成仓库，从初始失败日志开始，检查 path:line 证据和 patch hash，批准后运行测试。
4. 取舍：先以单 Agent 和词项/代码结构检索建立可测基线；只有评测显示多 Agent 或语义检索有净收益才增加。
5. 结果：报告评测样本数、定位/修复指标、失败案例、调用 token、估算成本与安全测试结果。没有实际数据前，这一步保持空缺。
